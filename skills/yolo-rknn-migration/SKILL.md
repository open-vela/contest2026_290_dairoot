# YOLO 迁移到 RKNN NPU

交付能在目标板上正确检测的模型与运行器，保证转换前后使用相同的输入和后处理。以本项目 YOLO11n 实现为参考；其他 YOLO 版本、分割/姿态模型或自训练类别需要重新核对接口。

## 输入与项目定位

确认 YOLO 版本、任务、权重来源/类别、目标 SoC、输入尺寸、转换机、Toolkit2/runtime 版本以及精度和延迟目标。定位包含 `linux-apps/miloco-server/` 的源码根为 `CONTEST_ROOT`；独立安装 Skill 时仍需目标源码，不依赖个人机器路径。

本项目有 `tools/convert_rknn.py`、`rknn_yolo.py` 和视频服务 `web.py`，使用 Rockchip Model Zoo 优化的 **YOLO11n 九输出 ONNX**，在 RK3576 上部署；Git 工作树不含 `.onnx/.rknn` 模型产物，已有 RKNN 可从[官方 Release 下载](../../docs/rknn-models-2026-09-19.md)。

转换和运行命令、源码定位见 [项目执行参考](references/project-workflow.md)。涉及新版本模型时，核对 [官方 YOLO11 示例](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolo11/README.md) 及对应版本的导出方式。

## 执行流程

### 1. 先核对模型图与输出

读取 ONNX 输入输出的名字、shape、dtype 和 layout，并记录权重/导出代码版本与哈希。不要仅凭 `yolo11n.onnx` 文件名认为可以复用后处理。

本项目输出是三尺度，每尺度依次为 box DFL、类别分数、score_sum，合计九路；box 是 64 通道，即 4×16 个分布桶；类别为 COCO 80 类。现有解码器忽略 score_sum，使用类别分数筛候选后计算 DFL。

普通 Ultralytics 导出的单输出模型不能直接接这个解码器。先选择匹配导出图，或按新模型契约实现对应后处理。自训练模型要同步类别数、标签表和筛选逻辑。

### 2. 固定预处理并建立参考检测

本项目输入：原 BGR 图等比例 letterbox 到 640×640，填充值 114，转 RGB，uint8、batch=1、NHWC；转换器以 `std_values=255` 完成归一化。推理侧不再重复 `/255`。

记录缩放比和补边偏移，后处理把框还原到原图坐标。使用同一套预处理比较 ONNX 与 RKNN，测试横图、竖图、边缘目标、小目标和无目标画面。新输入尺寸需要同步转换器、运行器及 stride/grid，不能只改 resize。

### 3. 转换 fp16 基线与 int8 候选

使用独立的 Toolkit2 转换环境，目标平台取实际 SoC。先保留不量化模型，再用真实场景代表性图像校准 int8；覆盖光照、距离、目标大小及空背景，不用少数演示图片代替验证集。

本项目简化转换器从当前目录读取固定文件名，参数只有可选的 `int8`，target 固定 RK3576。其他平台/文件名需要调整转换脚本或使用匹配的官方入口，不虚构 `--target/--model` 参数。

转换失败时记录具体算子、shape、工具版本；成功后检查模型输入输出再做固定样本对比。模型能加载不等于量化精度合格。

### 4. 接入 RKNN-Lite2 与后处理

检查 `load_rknn` 和 `init_runtime` 的返回值，以及实际加载 runtime/驱动版本。当前 `RknnYolo` 使用 RK3576 双核掩码；迁到其他芯片前核对核心数量与 API，不照抄掩码。

维持模型的类别索引；当前 `KEEP` 只展示 person、bed、cell phone、cat，不表示模型只有四类。新增显示类别修改筛选集合，不能删除 `CLASSES` 中间的条目导致编号错位。

复用 DFL → 按类别 NMS → 逆 letterbox 的顺序。当前候选阈值 0.25、NMS 阈值 0.45 是项目默认值；量化前后比较时使用相同阈值，不能靠调低阈值掩盖前处理或量化错误。

### 5. 先图像验收，再接视频

对固定测试集比较 fp32 ONNX、RKNN fp16 和 int8 的类别、分数、框与漏检/误检；有标注集时计算 mAP/召回，无标注时仅报告样例对照。核对无目标返回、输出尺寸与框坐标。

测预热后的网络耗时与完整 `detect` 耗时，并报告输入尺寸、核掩码、版本和分位数。当前命令行自测测的是预处理+网络+后处理，不能称为纯 NPU 耗时。

接视频时使用独立的解码后队列丢弃旧帧，避免推理阻塞解码。不要随意丢 H.265 压缩包破坏参考帧；单设 `appsink drop=true` 不能消除其回调阻塞。只有用户需要视频接入时才处理这部分，不为静态模型转换扩展成完整摄像头应用。

## 排障判断

| 症状 | 优先核对 |
| --- | --- |
| 九输出解码报索引/shape 错 | 是否拿了单输出原版图、输出顺序/布局是否改变 |
| 大量低分或完全漏检 | RGB/BGR、uint8/float32、重复归一化、输入 layout、量化集 |
| 框整体偏移或拉伸 | letterbox 比例/补边、stride、坐标还原 |
| 只有几种类别能出现 | `KEEP/KEEP_IDS` 过滤与完整标签表 |
| ARM 板运行 torch 出现 SIGILL | 核对具体 wheel 与 CPU 指令集；项目曾遇到二进制不兼容，不泛化为所有 ARM wheel 都不可用 |
| 视频越来越滞后 | 解码后队列、处理耗时、输入与输出速率；确认没有阻塞 streaming thread |
| 页面能看但检测没启用 | 项目允许回退到只推流；核对初始化日志和实际检测函数 |

## 交付结果

交付来源可追溯的模型、转换配置、校准/验证集说明、输入输出契约、对应运行器和固定样例结果。附精度与性能的实际验证范围；摄像头流可用、模拟队列测试通过都不能替代 NPU 检测验收。
